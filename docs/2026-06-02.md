### 1. MVC 전체 흐름 (DispatcherServlet 기반)

```
브라우저 (주소창 요청)
    |
    ▼
DispatcherServlet  ← 모든 .do 요청을 가로채는 관문
    |
    ▼
Controller  ← @RequestMapping으로 URL과 메소드를 매핑
    |
    ▼
Model (Service / DAO)  ← 비즈니스 로직 + DB 연동
    |
    ▼
결과값 → request / session에 저장
    |
    ▼
Controller → JSP로 포워딩
    |
    ▼
브라우저에 최종 화면 출력
```

> **핵심 규칙:** Spring MVC에서는 반드시 Controller를 거쳐야 한다.  
> URI 주소 끝에 `.do`가 붙으면 Servlet(DispatcherServlet)이 호출된다.

### 2. 어노테이션(Annotation) 이해

#### 어노테이션이란?

어노테이션은 **주석이 아니다.**  
코드를 읽는 사람이나 프레임워크가 "이 클래스(또는 메소드)는 어떤 역할을 한다"고 빠르게 인식할 수 있도록 붙이는 **마커(Marker)** 다.

```
기존 방식                       어노테이션 방식
----------------------------------------------
web.xml에 Servlet 등록         @Controller
복잡한 XML 설정                 @RequestMapping("/list.do")
if문으로 클래스/메소드 구분     @Autowired
```

XML과 if문으로 처리하던 복잡한 설정을 어노테이션 한 줄로 대체 → **소스 간결화 / 생산성 향상**

---

#### 어노테이션 제작 원리 (왜 이렇게 동작하나?)

어노테이션이 "마커"로 동작하려면 두 가지 설정이 필요하다.

#### ① Retention — 언제까지 살아있나?

| 옵션 | 동작 시점 | 설명 |
|------|-----------|------|
| `SOURCE` | 컴파일 즉시 사라짐 | `@Override` 같은 개발자용 힌트 |
| `CLASS` | .class 파일까지 유지 | 거의 사용 안 함 |
| `RUNTIME` | **프로그램 종료 시까지 유지** | Spring이 이 어노테이션을 읽고 동작함 |

Spring의 `@Controller`, `@RequestMapping` 등은 모두 `RUNTIME` 이다.  
→ Spring이 실행 중에 어노테이션을 찾아서 "아, 이 클래스가 Controller구나" 하고 인식하기 때문이다.

#### ② Target — 어디에 붙이나?

| 옵션 | 위치 | 용도 |
|------|------|------|
| `TYPE` | 클래스 위 | 클래스 찾기 (`@Controller`, `@Component`) |
| `METHOD` | 메소드 위 | 메소드 찾기 (`@RequestMapping`) |
| `FIELD` | 멤버변수 위 | 의존성 주입 (`@Autowired`) |
| `CONSTRUCTOR` | 생성자 위 | 생성자 찾기 |
| `PARAMETER` | 매개변수 옆 | 파라미터 바인딩 (`@RequestParam`) |

```java
// 클래스 위 (TYPE)
@Controller
public class BoardController {

    // 멤버변수 위 (FIELD)
    @Autowired
    private BoardService boardService;

    // 메소드 위 (METHOD)
    @RequestMapping("/list.do")
    public String list(Model model) {
        ...
    }

    // 매개변수 옆 (PARAMETER)
    public String detail(@RequestParam("id") int id) {
        ...
    }
}
```

---

#### Spring에서 @WebServlet이 없는 이유

순수 Servlet 방식에서는 `@WebServlet("/list")` 또는 `web.xml`에 직접 Servlet을 등록했다.  
Spring은 이 역할을 **DispatcherServlet 하나**가 전담한다.

```xml
<!-- web.xml -->
<servlet>
    <servlet-name>dispatcher</servlet-name>
    <servlet-class>org.springframework.web.servlet.DispatcherServlet</servlet-class>
</servlet>
<servlet-mapping>
    <url-pattern>*.do</url-pattern>
</servlet-mapping>
```

→ `.do`로 오는 모든 요청을 DispatcherServlet이 받고,  
→ `@RequestMapping` 어노테이션을 스캔해서 해당 메소드로 분기한다.  
→ 그래서 개별 Servlet마다 `@WebServlet`을 붙일 필요가 없다.

### 3. MyBatis 동작 순서 (Config.xml 기반)

#### 설정 파일 구조

| 파일 | 개수 | 역할 |
|------|------|------|
| `config.xml` | **1개** | DB 연결 정보, 전체 설정 |
| `mapper.xml` | **테이블당 1개** | SQL 문장 작성 |

#### 전체 처리 흐름

```
1. 사용자 요청 (브라우저)
    |
2. Controller가 요청을 받는다
    |
3. @RequestMapping → 해당 메소드 실행
    |
4. Model(DAO) 호출
    |
    ├─ [연결 단계] SqlSessionFactory
    │       config.xml 읽기
    │       → getConnection() / JDBC 연결
    │
    ├─ [SQL 단계] SqlSession
    │       mapper.xml의 SQL 문장 읽기
    │       → PreparedStatement로 전송 및 실행
    │       → ResultSet → List / VO에 자동 매핑
    │
    └─ disConnection() 자동 처리
    |
5. 결과값 → Controller → request/session에 저장
    |
6. JSP로 포워딩 → 화면 출력
```

#### SqlSessionFactory vs SqlSession 역할 구분

```
SqlSessionFactory         SqlSession
========================  ========================
JDBC Connection 담당       PreparedStatement 담당
config.xml 기반            mapper.xml 기반
연결 / 해제                 SQL 실행 + ResultSet 처리
                           List / VO 자동 매핑
```

#### config.xml 기본 구조

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE configuration PUBLIC "-//mybatis.org//DTD Config 3.0//EN"
    "http://mybatis.org/dtd/mybatis-3-config.dtd">

<configuration>
    <!-- db.properties 연결 -->
    <properties resource="db.properties"/>

    <environments default="development">
        <environment id="development">
            <transactionManager type="JDBC"/>
            <dataSource type="POOLED">
                <property name="driver"   value="${driver}"/>
                <property name="url"      value="${url}"/>
                <property name="username" value="${username}"/>
                <property name="password" value="${password}"/>
            </dataSource>
        </environment>
    </environments>

    <!-- mapper.xml 등록 -->
    <mappers>
        <mapper resource="mappers/BoardMapper.xml"/>
    </mappers>
</configuration>
```

### 4. db.properties 분리 

#### 현재 구조

```
config.xml  ──→  <properties resource="db.properties"/>
                        |
                 db.properties
                 ─────────────────────────────
                 driver=oracle.jdbc.driver.OracleDriver
                 url=jdbc:oracle:thin:@localhost:1521:XE
                 username=YOUR_ID
                 password=YOUR_PASSWORD
```

#### 보안 측면 분석

| 항목 | config.xml 직접 작성 | db.properties 분리 |
|------|---------------------|-------------------|
| 가독성 / 유지보수 | 설정과 DB정보가 섞임 | **DB정보만 따로 관리** ✅ |
| 환경별 전환 (dev/prod) | 매번 config.xml 수정 | **properties 파일만 교체** ✅ |
| Git 보안 (.gitignore) | config.xml 전체를 제외해야 함 | **db.properties 하나만 제외** ✅ |
| 파일 자체 암호화 여부 | ❌ 평문 | ❌ 평문 (동일) |

#### 결론

`db.properties`를 **일반 파일(plain text)로 저장**한 현재 방식은,  
config.xml에 직접 쓰는 것보다 **관리 편의성과 Git 보안 측면에서 유리**하다.

단, 파일 자체는 평문이므로 서버에 직접 접근할 수 있다면 노출된다.  
실무에서의 추가 보안 조치는 아래와 같다:

```
현재 (학습 단계)         실무 수준
─────────────────────────────────────────────────────
db.properties 분리       + .gitignore에 db.properties 등록
                         + Jasypt 라이브러리로 패스워드 암호화
                         + 환경변수(OS Environment Variable) 사용
                         + AWS Secrets Manager / Vault 연동
```

지금 단계에서는 **`.gitignore`에 `db.properties`를 추가**하는 것만으로도 충분한 기본 보안이 된다.

```
# .gitignore
db.properties
```
